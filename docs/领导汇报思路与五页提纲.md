# 领导汇报思路与五页提纲

整理日期：2026-11-11。按当前代码能力编写，尚未制作 PPT。提效数字按本人要求留空，后续用实测结果补充。

## 1. 汇报主线

原定五页结构可行，建议围绕一条主线组织：**传输维护人员提出业务规则，用 AI 编程助手实现工具，再通过现场试用迭代，改善采集、核对和问题跟踪。**

标题建议：**《AI 辅助开发机房资产盘点系统——传输维护场景的数字化提效实践》**。

这里的 AI 价值首先是辅助开发系统。上线后的扫码、汇总、普通字段比对和权限校验主要由程序规则执行；系统内的 AI 分析为可选辅助，目前不作为主要成果或自动验收依据。第二页使用“原人工流程／现系统流程”，避免把数字化的全部收益归因于大模型推理。

五页分别回答：取得什么变化、为什么能改善、做出了什么、怎样借助 AI 做出来、如何稳定运行并推广。成果页不堆功能，功能页不堆全部菜单，案例页只讲一个完整故事。

## 2. 第一页：先呈现业务价值与阶段成果

**建议标题：从手抄汇总到扫码核对，提升机房资产盘点效率。**

页面上方用一句话交代场景：

> 面向传输设备、传输综合柜和 ODF／IODF 机架盘点，解决人工记录、反复核对、资料分散和问题难跟踪等问题。

中间突出三项变化，使用大字号和统一强调色：

| 成果方向 | 可先呈现的变化 | 待填实测指标 |
|---|---|---|
| 现场采集提效 | 扫码填写、条码模糊查找、未盘优先，减少手抄和重复翻找 | 单机房现场盘点：____ 人时 → ____ 人时 |
| 后台核对提效 | 综资、现场、资产集中展示，规则定位差异，直接导出当前结果 | 单机房后台整理：____ 人时 → ____ 人时 |
| 问题处理可追踪 | 问题确认、拼销核实、责任处理、复核验收有记录 | 已确认问题：____；已验收闭环：____ |

页脚小字填写统计范围：截至 ____，试点 ____ 个机房、____ 台设备、____ 架 ODF／IODF。

没有数字前突出流程变化，不使用“节省 80%”“准确率 100%”等估算。待判断、待处理数量不能算作已确认错误或已整改成果。

**建议画面**：三张成果卡片，下方一条“清单 → 扫码 → 比对 → 处理 → 验收”简图。业务背景控制在两行内，给成果留主要空间。

## 3. 第二页：原来怎么做，现在怎么做

**建议标题：减少重复录入和往返沟通，让盘点资料可查、问题可追。**

| 环节 | 原人工流程（按实际经历确认） | 现系统流程 | 改善点 |
|---|---|---|---|
| 任务准备 | 分发 Excel／纸质清单，人工说明版本 | 按机房导入、按片区领取，旧任务更新受控 | 统一清单和责任人 |
| 现场采集 | 手抄、拍照，回办公室再录入 | 小程序扫码，登记柜位、型号、盘盈盘亏及机架 | 减少二次录入，采集格式统一 |
| 资料核对 | 多份表逐项找条码、名称和地点 | 按地点限定、按资源关联，集中展示三系统差异 | 减少切表和重复查找 |
| 疑难处理 | 现场与后台反复联系，处理进度分散 | 管理员修正、人工拼销、按责任建单反馈 | 信息有统一入口和处理记录 |
| 历史追溯 | 翻聊天记录、旧文件，版本难分 | 本人完成任务可查，后台保留来源、修正和工单历史 | 便于查证和复核 |

质量提升应讲“如何控制”：必填和重复检查、机柜／机架区分、完成后锁定、管理员修正留痕、型号人工判断、验收读取最新资料。只有取得抽检数据后，再填写差错率改善。

页角可注明 AI 的两层作用：

- **本次重点**：AI 编程助手辅助实现功能、检查逻辑、修复问题并迭代。
- **辅助能力**：系统内已有 AI 问题解释和分析报告，严谨性继续优化，不代替业务判断。

“原来 AI 是手抄”应改为“原来人工手抄和纸质盘点”。闭环原流程建议写“难以持续跟踪”，避免未经统计就断言以前完全没有闭环。

## 4. 第三页：系统能力与界面

**建议标题：小程序采集、后台核对，覆盖设备与机架盘点。**

主要放三组当前页面截图，每张只标两至三个重点：

| 截图 | 建议标注 |
|---|---|
| 小程序设备／机架盘点 | 类别提示、扫码采集、条码搜索、ODF／IODF 独立登记 |
| 后台三系统比对 | 同一资源三行展示、差异集中呈现、型号人工判断 |
| 拼销或整改工单 | 盘亏盘盈人工核实、跨机房提示、责任及处理记录 |

底部用四个功能组即可：任务管理、现场采集、资料核对、问题处理。账号、二维码和 AI 设置等辅助能力放备注或备份材料，不抢占主线。

覆盖类别可写“省干设备、交换机、OTN、SPN、OLT、SDH、PTN 等，使用统一设备类别及采集流程”。这是盘点管理覆盖，不是与上述全部网管已自动对接。

画面注释保留两项实际边界：

- 传输综合柜随设备采集；综资目前提供柜位，柜条码主要核对现场与资产。
- ODF／IODF 已独立采集并与资产核对，综资机架基线待补，不宣称机架已实现完整三方自动比对。

截图使用当前页面，隐藏人员姓名、手机号、IP、真实条码、邮箱及机房敏感信息。现有手册图片包含早期示意，不能直接当作当前系统截图。

## 5. 第四页：一个案例讲清如何与 AI 编程助手协作

**建议标题：从“盘亏盘盈怎么处理”到可操作的拼销功能。**

这是本次对话中实际经历的需求迭代，适合说明业务人员如何将经验转化为规则。下面是交互内容的归纳，不作为逐字聊天截图，也不虚构真实完成案例。

| 关键步骤 | 与编程助手交互的重点 | 形成的结果 |
|---|---|---|
| 1. 提出业务问题 | 甲机房盘亏、乙机房盘盈，可能是同一台设备，不应分别当成两项独立异常 | 明确需要盘亏盘盈拼销入口 |
| 2. 澄清判断规则 | 只能推荐候选，必须人工确认；型号或柜条码相同不能证明同一实物 | 确认依据必填、保留原记录、支持撤销 |
| 3. 明确跨机房处理 | 合并结果归实际找到机房，原机房保留迁出提示，外部系统另办调拨 | 业务归属与调拨待办有据可查 |
| 4. 试用后反馈优化 | 打开弹窗慢，不应默认加载全部盘亏盘盈 | 默认最多推荐 15 条，无推荐时按条件查询 |
| 5. 验证交付 | 检查候选范围、重复拼销、来源变化、撤销和导出是否符合规则 | 以页面验证和测试支撑功能交付，继续现场试用 |

建议展示“业务需求 → 规则澄清 → 编码实现 → 验证 → 现场反馈迭代”五步，每一步配一句真实业务要求。可从已有对话提炼两至三段，不需要展示代码大段截图。

页面下方将案例放回全流程：

> 导入并下发任务 → 小程序盘点 → 三方规则比对 → 人工拼销／问题建单 → 处理反馈 → 复核验收。

讲解重点：“我负责业务定义、例外情况和验收标准，AI 编程助手辅助实现；试用中发现的问题继续转化为改进要求。”不能讲成系统内 Agent 一句话自动下发任务、自动整改外部系统。

若尚无已验收的完整真实工单，本页演示已实现的拼销及工单入口，后半段说明验收机制；实际闭环成效等真实案例完成后再补。

## 6. 第五页：困难、改进与推广条件

**建议标题：从个人试用走向稳定运行，逐步复制推广。**

| 困难 | 已采取的措施 | 下一步 |
|---|---|---|
| 业务规则复杂：同名、多条码、设备与机架混淆 | 拆清对象、按地点限定范围、规则核对与人工判断结合 | 补齐机架综资基线，持续用真实样本校验 |
| 现场界面与数据量变化 | 增加搜索、未盘优先、盘盈纠错、查询后展示及候选分页 | 继续实测多机房规模下的性能与易用性 |
| 个人电脑部署依赖电源和网络 | 提供启动、切换和连接自检脚本 | 申请单位批准的常开主机和稳定网络，补监测与备份恢复 |
| 资料及访问安全 | HTTPS 和隧道接入，后台邮箱验证、独立账号、角色权限与操作留痕 | 按单位要求评估部署网络、第三方代理与外部模型的数据边界 |

当前接入方式建议写：

> 现场小程序通过 HTTPS 与 Cloudflare Tunnel 接入本机后端，异地管理端增加邮箱验证、后台账号及权限校验。

不能写成“单位内网专线”“完全不走公网”“绝对不会泄露”。当前关机、休眠、断网或服务停止都会影响现场使用；“线下测试”也不是无网离线盘点。安全措施已在代码中具备相应校验，但本次未重新检查云端实时策略，不作为安全认证结论。

推广路线建议分三步：

1. **先在传输维护内试点**：选相近规模机房，记录实际人时、录入质量和已验收问题，形成一套模板与规则。
2. **再完善运行保障**：落实常开环境、备份恢复、运维责任和账号开停，补齐机架资料链路。
3. **再评估复制**：向其他片区、类似网络设备或站房盘点场景推广；不同专业先确认数据口径和管理规则，不能直接照搬型号判断或资产关联规则。

建议页末提出明确支持事项：**试点范围、常开部署资源、资料维护责任人和验证时间安排**。领导既能看到成果，也知道下一步需要什么支持。
