# 协作管理员与异地访问

更新：2026-11-02。独立账号、协作权限及远程后台已配置，正式页面已构建，Cloudflare Access 应用、邮箱验证码及专用域名路由已建立，本机远程开关已启用。入口仅允许 Cloudflare 与本机 `.env` 名单中一致的获准邮箱通过验证，随后仍需使用后台账号和密码登录；未改动当前小程序域名或现场运行模式。

## 创建管理员 B

主管理员打开「账号管理 → 新建空白账号」，填写登录编码（例如 `admin_b`）、姓名，角色选择「协作管理员」，设置 12—128 位独立密码并启用。后台账号不需要微信 openid；登录时使用这里填写的登录编码和密码。不要共用主管理员账号。

现有现场账号也可以编辑升级为管理员，升级时必须同时设置密码。已有管理员可在列表中重置密码。密码采用加盐哈希保存，不在列表、响应或审计记录中返回。修改角色、权限、登录编码、启停状态或密码会使旧会话失效。环境变量 `INVENTORY_ADMIN_PASSWORD` 仅供首次初始化，不再在服务重启时覆盖后台设置的新密码。

登录页的“忘记密码？”提供两种恢复说明：协作账号由完整管理员在账号管理中重置；完整管理员也无法登录时，在运行系统的 Mac 上使用 [本机密码恢复工具](../scripts/mac/reset_admin_password_mac.command)，由本人隐藏输入两次新密码。工具先备份数据库，再原子更新目标密码、登录版本和本机恢复审计，不开放公网免登录重置接口，也不把任意获准邮箱当作主管理员身份。

| 操作 | 完整管理员 | 协作管理员 |
|---|---|---|
| 查看所有机房、盘点数据、资产表、三方比对及导出 | 可以 | 可以，不按登记片区限制 |
| 人工比对、型号判断、修正设备/机架/随设备汇总的机柜数据 | 可以 | 可以 |
| 补录机架、作废误录机架或盘盈记录 | 可以 | 可以，保留原有原因及历史要求 |
| 补地点编码、更新已有任务的综资基线 | 可以 | 可以 |
| 新建/导入/派发/作废任务、导入资产表、维护二维码资料 | 可以 | 不可以 |
| 账号、角色、密码、系统及 AI 配置 | 可以 | 不可以 |
| 执行 AI 分析/聊天、整改审核/派发/验收 | 可以 | 不可以；历史报告和台账可查看 |

协作权限由后端按请求方式和接口路径检查，未明确开放的新接口默认拒绝。页面隐藏按钮只是辅助展示。不能停用、删除或降级最后一个可登录的完整管理员。旧测试会话在关闭测试登录后也会失效；管理员访问现场接口同样受到来源限制。

多名管理员可以同时登录。资料修正仍按现有业务规则由后保存的有效值覆盖，操作历史保留；这次没有新增多人实时协同编辑或编辑锁。

## 已实现的远程入口

后台入口：`https://admin.equip-inventory.xyz`。目前仅允许上述邮箱；其他管理员需先完成下文的邮箱放行和账号创建，不能直接共用现有账号。

当前方案直接复用后端 8000 服务，按域名隔离远程后台，不需要新增 Caddy、8081 端口或修改转发 IP：

```text
浏览器 → HTTPS 后台专用域名
       → Cloudflare Access 邮箱验证
       → 现有 Tunnel → 127.0.0.1:8000
       → 后端再次验证 Access JWT、应用 AUD、有效期和邮箱白名单
       → 加载 remote_dist 正式页面
       → 使用后台独立账号登录，再按完整/协作权限操作
```

前后端使用同一个后台域名及相对 `/api` 地址，远程电脑不会请求它自己的 `127.0.0.1`。旧小程序 `api` 域名继续按原规则工作；Access 凭据不能拿到小程序域名绕过管理员来源限制。本机 5173 开发服务继续保留。

只接收配置的官方团队域签发的 RS256 Token，核对 issuer、audience、过期时间、签发时间、应用类型和精确邮箱白名单；单独伪造邮箱请求头无效。页面、静态文件和 API 全部经过验证。配置不全时远程入口拒绝访问，原小程序和本机后台继续使用。验证公钥有缓存和超时，取公钥不占用处理现场请求的事件循环。

正式页面只从 `admin_web/remote_dist` 中读取，拒绝隐藏文件、源码目录、数据库、路径穿越和目录外的符号链接。远程响应设置禁止缓存及禁止嵌入其他站点的保护头。

实现采用 Cloudflare 的[服务端 JWT 验证方式](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)，不依赖关闭管理员 IP 限制，也不把公网来源伪装成本机来源。

## 已完成的 Cloudflare 配置及后续维护

已通过已登录的 Cloudflare 控制台创建后台应用和指定邮箱策略，添加 One-time PIN，并在现有 Tunnel 新增后台专用域名路由。以下保留配置位置和维护方法；无需向他人发送密码、隧道 Token、API Token 或验证码。

### 1. 团队域名与邮箱验证码

打开 [Cloudflare 控制台](https://dash.cloudflare.com/)，进入 Zero Trust。

- 在 Settings → Team name and domain 中查看团队域名，完整形式为 `https://你的团队名.cloudflareaccess.com`。
- 当前团队已启用 One-time PIN，后台应用只选用这一登录方式。
- 后续在 Integrations → Identity providers 维护登录方式；不能只填邮箱却没有可用的登录方式。

参考：[团队域名位置](https://developers.cloudflare.com/cloudflare-one/faq/getting-started-faq/)、[添加 One-time PIN](https://developers.cloudflare.com/cloudflare-one/integrations/identity-providers/one-time-pin/)。

### 2. 只允许指定邮箱的后台应用

已建立 Self-hosted 公网 Web 应用，可在 Zero Trust → Access controls（部分界面名为 Access）→ Applications 查看或维护：

| 设置 | 填写 |
|---|---|
| 应用名称 | 资产盘点后台 |
| Public hostname | `admin.equip-inventory.xyz` |
| Path | 留空，覆盖整个域名，包括 `/api` 和 `/assets` |
| 登录方式 | One-time PIN |
| Policy action | Allow |
| Include 条件 | Emails，填写实际获准邮箱（如 `owner@example.com`） |
| HTTP Only Cookie | 已开启 |

不能使用 Everyone、Bypass，也不能把「Login Methods: One-time PIN」单独作为 Include 条件放行所有邮箱。云端策略和本地邮箱白名单必须同时匹配。[官方邮箱策略说明](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/common-policies/)

团队域名和 **Application Audience (AUD) Tag** 已配置到本机。以后如重建应用，需从应用的 Additional settings 获取新 AUD，并同步维护本机配置；不要沿用被替换应用的值。[AUD 获取位置](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/)

### 3. 本机配置与已发布路由

当前 `.env` 的远程开关已设为 `1`，后台域名、团队域名、AUD 和邮箱白名单均已配置，并已完整重启后端加载。以下仅为维护格式示例，不包含实际 AUD：

```dotenv
INVENTORY_REMOTE_ADMIN_ENABLED=1
INVENTORY_ADMIN_HOST=admin.equip-inventory.xyz
CLOUDFLARE_ACCESS_TEAM_DOMAIN=https://你的团队名.cloudflareaccess.com
CLOUDFLARE_ACCESS_AUD=该后台应用的AUD
INVENTORY_ADMIN_ALLOWED_EMAILS=获准的完整邮箱
```

`INVENTORY_ADMIN_IP_RESTRICTION_ENABLED=1` 及原 IP 白名单保持不变。多邮箱以英文逗号分隔；以后允许 B 登录时，必须同时更新 Cloudflare Allow 策略的 Emails 和本机 `INVENTORY_ADMIN_ALLOWED_EMAILS`，再为 B 创建并启用独立的「协作管理员」（内部权限 `collaborator`）后台账号。仅添加邮箱或仅创建后台账号都不足以完成异地访问。

维护者确认配置有效后重启一次后端加载 `.env`。双击项目根目录的 `scripts/mac/prepare_remote_admin_mac.command` 可构建并检查；命令行 `./scripts/mac/prepare_remote_admin_mac.command --check-only` 只检查已有页面。

脚本先在临时目录构建，成功后才替换正式页面，构建失败保留旧页面。它不会改 `.env`、重启服务或隧道、切换小程序模式，也不会输出 Token、AUD 或邮箱。退出码 `0` 是本机自检通过，`2` 表示配置等尚未就绪，`1` 表示构建/文件操作失败；均不能代替真正的云端访问验收。

已在现有 Tunnel 中新增 Published application 路由，后台域名的 DNS CNAME 指向该 Tunnel：

| 设置 | 填写 |
|---|---|
| Hostname | `admin.equip-inventory.xyz` |
| Service 类型 | HTTP |
| Service URL | `http://127.0.0.1:8000` |
| HTTP Host Header | 保留后台域名；如果手动填写，只填 `admin.equip-inventory.xyz` |
| Protect with Access | 已开启，绑定这个后台应用的团队和 AUD；后端仍会独立验签 |

保留原 `api` 路由，不能在小程序域名上添加浏览器邮箱验证。运维时应确保后台敏感页面与 API 不被 CDN 缓存，并使用 HTTPS；本次未修改 Cloudflare 的缓存规则、HSTS 或强制 HTTPS 设置，不能将建议当成已完成的控制台配置。不要发布 Vite 的 5173 端口或整个项目目录。官方路由位置见[隧道发布指南](https://developers.cloudflare.com/tunnel/get-started/)。

## 访问验收与使用限制

调整邮箱名单、应用、域名路由或发布页面后，应检查以下场景：

1. 未授权邮箱无法进入；指定邮箱收到验证码，验证后才能看到后台登录页。
2. 只有邮箱验证、没有后台账号 Token 时，数据接口返回 401；只有后台 Token、没有 Access 验证时，远程整站被拒绝。
3. B 可查看全部机房、比对和修正；账号管理、任务删除、系统配置等接口仍拒绝。
4. 小程序登录、扫码提交及本机后台保持正常；远程浏览器请求的 API 地址始终为后台域名 `/api`。
5. 未验证情况下访问 `.env`、数据库或源码均无法下载；已验证后也不会公开这些文件。

本地已用临时数据库、本地 RSA 密钥及模拟 JWKS 验证代码链路，完成正式页面构建和启用后的健康检查；后台域名直达本机且缺少有效 Access JWT 时返回 403。公网无身份访问后台根页面、`/api/admin/me`、`/assets/` 和 `/health` 均返回 302，转到团队的 Cloudflare Access 验证入口；原小程序 API 的 `/health` 返回 200。HTTP 后台入口实测返回 301，先转到同一后台域名的 HTTPS 地址。

真实邮箱验证及协作管理员账号登录已成功，刷新后会话保持，远程任务管理和已完成机房的 122 条盘点明细可正常加载。三方比对查询曾触发浏览器 10 秒超时，但后端对应请求均返回 200；同一任务本机只读比对约 0.12 秒，紧凑 JSON 约 2.43 MB。现仅将三方比对查询和「导出设备比对」的前端等待时间延长至 60 秒，其他接口仍保持原有 10 秒。

新页面已在真实远程会话中验证：所选同一机房的三方比对正常加载，显示设备 148 组、机架 39 组、未关联资源条码 19 个，资产范围共 58 个条码。「导出设备比对」按钮可用，本次仅延长其等待时间并通过类型检查及构建，尚未实际下载验证；不能据此认定 Excel 下载内容或全部权限场景均已通过验收。

当前 Mac 必须开机并保持网络及隧道运行。本机调测模式若会停止 Tunnel，异地后台也会一起断开；切回现场使用模式后恢复。长期多人使用宜迁到单位允许的常开服务器和稳定网络。
